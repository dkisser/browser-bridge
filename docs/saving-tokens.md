# 省 token 的原理：信噪比

模型按 token 计费，上下文窗口是固定预算。一条信息进入上下文，花掉的不只是它自己的 token：窗口会被填满，早进来的噪声会挤占后面会话里真正需要的信号。噪声的成本是双份的——自己占一份，挤出去的占一份。

省 token 的动作因此发生在信息进入上下文之前。页面按原始形态提供信息，模型按预算消费信息，两者之间需要一个筛选层。这个筛选层做的事有一个名字：**信噪比**。

## 名词：信噪比

信噪比是通信术语：信号与噪声的比值。信道带宽固定时，比值越高，能传的信息越多。搬到这里：上下文是信道，token 是带宽，任务需要的内容是信号，其余一切是噪声。省 token 的本质是**在信息进入信道之前提高信噪比**。

先做一个区分：不是压缩，是筛选。压缩是把信息编码得更短，筛选是把噪声挡在信道外。被筛掉的部分没有损失信息，因为噪声本来就不携带任务需要的内容。判断标准只有一个：这个字符参与下一步决策吗。参与，是信号；不参与，是噪声。

信号还有一个性质：**信号是任务的函数，不是页面的属性**。同一个新闻页，任务是读正文时，正文是信号；任务是找相关阅读时，正文成了噪声，文末的链接列表成了信号。不存在"这个页面的信号是什么"这种客观答案，只有"这个任务在这个页面上需要什么"。一切筛选都以任务为前提。

## 噪声是什么

看清噪声的来源，要先看清 HTML 是什么。HTML 是页面的机器形态，不是阅读形态。它是写给渲染引擎的指令：脚本、样式、布局属性、模板结构，每一部分都对"画出一个页面"有用，对"回答一个问题"基本无用。一份典型新闻页 HTML 的大致构成：脚本和样式占最大头，导航、页脚、广告、相关阅读占其次，隐藏内容和不渲染的模板再占一部分，正文排在最后，占比一到十分之一。

虚拟列表是另一种噪声制造机。Gmail 和 GitHub 的现代列表只把可视区域的行挂载进 DOM，其余行不存在。页面的 DOM 本身已经是一种采样，采样范围随滚动位置变化。在这个环境里，"整页"是个模糊概念：DOM 里没有整页。

## 一组实测

下面是 2026 年 9 月 15 日的一组实测。测量工具是 Browser-Bridge 的 MCP 工具，浏览器是登录态的真实 Chrome，字符口径为 JS String.length。第二列是整页 `get_html` 的字符数，全部被十万字符上限拒绝，数字取自拒绝信息。第四列是任务真正需要的内容，用定向读取实测：

| 页面 | 整页 HTML | 信号 | 信噪比 | 定位开销（snapshot） |
|---|---|---|---|---|
| 东财文章页 | 169,318 | 正文 2,318 | 1:73 | 8,154 |
| GitHub notifications | 303,176 | 通知列表 364 | 1:833 | 3,312 |
| Gmail 收件箱 | 324,078 | 邮件列表 546 | 1:594 | 2,982 |

表里有三个读法。

第一，HTML 形态是噪声的重灾区。三个页面携带的 HTML 在 17 万到 32 万字符之间，信号只有几百到两千字符。最差的信噪比 0.12%：每 833 个进入上下文的字符里有一个是信号。

第二，snapshot 的定位成本稳定。三个页面用 3K–8K 字符就能看清结构、拿到容器位置。成本不随页面变大而显著增长，因为 snapshot 只保留交互元素和标题。

第三，Gmail 的整页 `get_text` 只有 2,940 字符，是三个页面里最小的。这个数字有欺骗性，例三里专门讲。

## 例一：新闻网站，东财文章页

任务是读一篇文章的正文。

原始路径：`get_html body`，169,318 字符，其中正文 2,318 字符，信噪比 1:73。这个读取被 MCP 层拒绝：超过十万字符的结果不允许进入上下文。就算放开上限，进入上下文的也是十六万字符噪声。

先看文本形态。整页 `get_text` 是 5,175 字符，其中正文 2,318 字符，噪声 2,857 字符，是信号的 1.2 倍。文本形态比 HTML 干净得多，噪声依然超过信号一倍。

正文容器的真实身份是 `<div id="ContentBody">`，一个无语义标签。靠语义猜测——article、.content、.post——在这类页面上必然落空。门户 CMS 的正文容器就是裸 div。

改进路径分两步。snapshot 用 8,154 字符展示页面结构，正文容器在其中。再 `get_text` 只读这个容器：2,318 字符。信号一模一样，噪声降到零。总成本 10,472 字符，是原始路径的 6%。

这个对比在现实里发生过。Browser-Bridge 项目记录过一次真实事故：agent 在东财类新闻页上连续猜错六个选择器，随后用整页 `get_html` 拉了 420K 字符的导航、广告和侧栏，正文淹没在里面。原始路径的成本不止 token，还有模型在噪声里找信号花的注意力。

## 例二：GitHub notifications

任务是确认哪些通知需要处理。

通知列表本身只有 364 字符：类型、仓库、标题、时间，一行一条。同页 HTML 303,176 字符，信噪比 1:833，三个页面里最极端的。

这个比值的原因值得看清。GitHub 是重交互应用，HTML 里装着完整的 React 运行时、路由代码、样式表和 SVG 图标。这些是页面运行的全部，是任务信号的零。模型读完全部信号只要 364 字符，读它的机器形态要三十万。

文本形态同样不干净：整页 `get_text` 1,018 字符，是信号的 2.8 倍。导航、侧栏、页脚跟着文本一起进了上下文。

snapshot 用 3,312 字符完成定位：通知列表的容器、每条通知的可点区域、页面上其他可交互元素，全部在表里。模型从头到尾不接触其余三十万字符。

## 例三：Gmail 收件箱

任务是找到某封邮件。

邮件列表 table 546 字符，同页 HTML 324,078 字符，信噪比 1:594。

Gmail 的整页 `get_text` 只有 2,940 字符，容易被读成"Gmail 信噪比不错"。这个读法错了，原因在虚拟列表：Gmail 只把可视区域的十几行邮件挂载进 DOM，DOM 里没有整页。2,940 字符是"碰巧渲染的这十几行"加上侧栏和面板，不是页面的文本量。换一个滚动位置，数字就换一个。

拆开来更清楚：2,940 字符里列表信号 546 字符，其余 2,394 字符是侧栏和面板。文本形态下噪声是信号的四倍。整页读取在这个页面上是双重的坏：噪声高，而且不完整——只覆盖已挂载的行。

虚拟列表还有第二个坑：行的 class 不稳定，不同行携带的类名不一样。逐行 class 选择器在 Gmail 上匹配不到行是常态，匹配到了也经常只匹配一部分行。

## 两种失败的读取模式

实测之外，项目记录里还有两种反复出现的失败模式，都发生在压力之下。

第一种是散弹枪猜选择器。一个选择器失败之后，紧接着试 .entry-content、.article-body、.post-content。一次失败意味着对 DOM 的信息量是零，第二个猜测建立在零信息上，命中靠运气。正确的响应是停下来观测：snapshot 一次，或者直接用错误信息附带的最大文本容器列表——第一个失败已经把 DOM 的观察结果送回来了。

第二种是贪心补偿。连续失败之后放弃精确读取，转而抓整页：`get_html body`、`get_text body`。实测数据解释了为什么这个模式无效：整页 HTML 全部超过十万字符上限，在进入上下文之前就被拒绝；整页文本裹挟着两倍到四倍噪声。贪心补偿在两个方向上都到不了目的地。

两种模式的共同点：把读取当成赌博，而不是测量。信噪比视角下，每次读取之前应该答得出一个问题——这次读取的信号是什么，在哪个容器里。

## 工程上的三个手段

信噪比可以由模型自己提，也可以由工具强制。工具强制的更可靠，因为它不依赖模型当时的判断。对应三个手段：

1. **观测先行**。snapshot 是结构视角：交互元素和标题，带 `@eN` 引用，输出有预算和分层，文本超长时截断并标注。成本 3K–8K 字符，换来后续每一次读取都有目标。模型面对的文案就是行为，所以"先观测"被直接写进工具描述。
2. **定向读容器**。用 snapshot 的 `@eN` ref，或者错误信息里给出的候选容器，只读信号所在的那一小块。渲染文本（innerText）进一步排除隐藏子树和脚本样式，换行与屏幕一致。
3. **上限兜底**。十万字符硬上限让整页 dump 无法进入上下文。拒绝信息里附带精确字符数——拒绝本身成了最好的反面教材，数字会留在模型的下一次决策里。

## 代价与闭环

筛选是有损的：后来被证明需要的内容，可能已经在筛除时丢掉了。完整的机制保留一条回源的路：页面仍在浏览器里，随时可以用更细的粒度重读，用逃生舱拿原始 HTML，对虚拟列表滚动后再读一次容器。省 token 靠筛选，不漏信号靠回源，两者构成闭环。
