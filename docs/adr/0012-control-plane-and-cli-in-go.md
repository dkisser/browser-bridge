# Reimplement the control plane and CLI in Go

The control plane (`bridge-core`) and CLI (`bridge-cmd`) ship as `bun build --compile` binaries: 66 MB and 61 MB respectively, of which the overwhelming majority is the embedded Bun runtime — the application code is ~4,650 lines of TypeScript. The compiled-binary path has also proven fragile: `xsschema` (a transitive dependency via fastmcp) dynamically imports optional peers inside the compiled binary, which forced four packages into `dependencies` that no source file imports and once produced silent feature loss (the MCP server on 3003 missing from a built artifact). The service lifecycle is a 689-line bash template (`install/bridge.sh.tmpl`) with its own BATS suite. The motivation for change is explicitly *not* throughput — the workload is a handful of loopback connections carrying low-frequency JSON — but distribution size, resident memory, elimination of the compiled-binary fragility class, and absorption of the bash service layer into the binary. It is also, honestly, a learning vehicle for Go on the maintainer's side.

Both are reimplemented in Go on the `go-rewrite` branch with the wire protocol byte-identical: same loopback ports (3001 inbound WebSocket, 3002 browser-facing WebSocket + pairing HTTP, 3003 MCP Streamable HTTP), same JSON envelope, same pairing handshake. The published extension works against either implementation without modification, which makes the completion standard objective: same wire behavior, different runtime. No IDL is introduced — Go structs are the schema. MCP tool input schemas are hand-built `jsonschema.Schema` values matching the TS zod/xsschema output field for field (struct reflection cannot express `default`, `format`, or the draft-07 dialect xsschema emits); wire parity is proven by golden-JSON fixtures and a `tools/list` diff against the Bun build; after merge, `tygo` generates the TS-side protocol types from the same Go structs for the extension. The extension stays TypeScript and is untouched throughout.

## Considered Options

- **Stay on Bun and shrink artifacts (UPX, Node SEA, Deno compile, esbuild)**: every single-file distribution of a TS runtime embeds the runtime itself, keeping the floor in the tens of MB; this fixes neither the xsschema fragility class nor the bash service layer.
- **Rewrite only the daemon, keep the Bun CLI**: leaves a Bun runtime in the distribution and forfeits most of the size win; the CLI is 590 lines and shares the protocol code anyway.
- **Adopt an IDL (protobuf / OpenAPI / AsyncAPI)**: protobuf changes the wire format (breaking wire-compatibility) or degenerates into a type generator via proto3 JSON mapping; OpenAPI cannot express WebSocket and the HTTP surface is three pairing endpoints; AsyncAPI fits WS channels but its Go codegen is immature. The project's public schema-bearing interface already exists — MCP on 3003; the 3001/3002 protocol is an internal detail between three components we own, and IDLs earn their keep on public boundaries with independent evolvers.
- **Generate Go types from TS with quicktype**: popular, but its Go output is widely considered unidiomatic (heavy `interface{}`, boilerplate serializers) and the v26 modernization skipped the Go backend; the current ecosystem consensus is Go-struct-first with `tygo`/`guts` generating the TS side.
- **Hand-maintained dual type definitions with contract fixtures**: workable at this protocol size (20 commands, 5-field envelope) and indeed how the transition runs; post-merge the Go structs become the single source via tygo, so dual hand-written definitions never become permanent.

## Consequences

- The repo becomes bilingual: TS/Bun (extension, `packages/shared`) and Go (control plane, CLI). Protocol evolution on `main` is frozen for the duration of the rewrite; an unavoidable change must be mirrored to the `go-rewrite` branch within the week.
- Merge gate: the contract fixture suite is green against both implementations; all 22 MCP tools work end-to-end; the maintainer dogfoods the Go build as the daily driver for two weeks; the installer installs the Go build. On the branch the TS control plane, the TS CLI, the bash service router (`install/bridge.sh.tmpl`) + `install/launchagent.plist.tmpl`, and the service-layer BATS suite (`install/tests/bridge.bats`) are already deleted (git history retains them); `install.sh` stays bash and keeps `install/tests/install.bats`.
- Transition mechanics: the TS CLI survives the early phases with `protocol`/`client` vendored into `apps/cli/src/` — it is the spike's test driver until `cmd/bridge` replaces it. The deleted TS control plane remains available in a `main` worktree for fixture extraction and behavioral comparison.
- `packages/shared` keeps its hand-written extension-side logic (policy, snapshot); the protocol types (envelope, command contracts) become tygo-generated from Go structs post-merge, adding a generation step to the TS dev flow.
- Release keeps the existing script pipeline (`.github/scripts/build-binaries.sh` + `build-tarball.sh` + `release-binaries.yml`), now invoking `go build` with `CGO_ENABLED=0` for darwin/linux × amd64/arm64. goreleaser was evaluated and rejected: the pipeline already provides the build matrix, per-file SHA-256 sidecars, and the custom tarball layout, and goreleaser would have needed shims for all three. The xsschema class of compiled-binary dynamic-import failures disappears by construction — Go binaries are statically linked with no module loading at runtime.
- Testing: Go unit tests cover router/pairing/state; the ~4,400-line bun suite is not ported — behavioral parity is proven by the black-box contract suite (golden JSON fixtures, `tools/list` diff).
- Library choices: `coder/websocket` for both WebSocket servers (the 2026 default for new projects; gorilla is maintenance-mode), `cobra` for the CLI, official `modelcontextprotocol/go-sdk` for MCP (`StreamableHTTPHandler`).
