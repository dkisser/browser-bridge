# Merge `ws-server` and `local-proxy` into a single `bridge-core` process

Originally the bridge split into two background binaries — `ws-server` on 3001 (the stateless router) and `local-proxy` on 3002 (the browser-facing bridge to extension). In practice the "server" half was never deployed in the cloud: defaults bind both to `127.0.0.1`, `local-proxy` ships a `DEFAULT_SERVER_URL` of `ws://localhost:3001`, and the install pipeline never opens a port — every user has run both processes on the same machine since v0.1.0. The split therefore bought nothing for the cloud-agent scenario it was drawn up for and cost a Bun runtime per binary (~60 MB uncompressed), a WebSocket upgrade hop between the two, and a full protocol encode/decode round-trip per direction inside one machine. The two halves are now a single `bridge-core` binary: one `Bun.serve` accepts three loopback ports (3001 WebSocket / 3002 status / 3003 MCP), `apps/bridge-core/src/server/` handles inbound commands from `bridge-cmd` and MCP clients, and `apps/bridge-core/src/client/` keeps the outbound WebSocket to the extension; the cross-process message path becomes an in-process function call and only the two wire-boundaries (CLI↔bridge-core and bridge-core↔extension) encode/decode. CLI stays a separate `bridge-cmd` binary because it is invoked per command by the user's terminal or an agent process; long-lived bridge logic does not belong inside it.

## Considered Options

- **Keep both binaries, share code via `@browser-bridge/websocket` (status quo)**: the cost was documented above; the deciding factor against it is that the split has no remaining workload separation to justify the second Bun runtime — the cloud deployment it was sized for is not in use, and re-introducing it later would mean adding a *new* cloud role (a public relay) rather than resurrecting a "user-local ws-server" that does double duty.
- **Merge into one process but keep the WebSocket hop inside it (still encode/decode twice per command)**: trivially cheap to write, but the second encode/decode exists only to preserve the original boundary shape and is pure waste — once the two endpoints share an address space, in-process dispatch is what you actually want.
- **Drop WebSocket for CLI↔bridge-core and use HTTP + SSE**: HTTP tooling is friendlier to debug, but the command protocol is bidirectional with push events (`welcome`, `online`, `offline`, `list_browsers`) and one-shot responses correlated by id; HTTP+ SSE would re-implement that framing for zero benefit and break every existing `--server ws://…` integration. Kept WebSocket.
- **Ship MCP as a separate `bridge-mcp` binary to shrink the main binary by ~5 MB**: real win on size, real loss on out-of-the-box UX — the user explicitly chose "install and it works" over saving 5 MB.

## Consequences

- The new top-level layout is `apps/bridge-core/` (was `apps/websocket/` + `apps/local-proxy/`) plus `apps/bridge-cmd/` (CLI, unchanged). `apps/websocket/` and `apps/local-proxy/` are deleted in the same PR; any code path that still imports `@browser-bridge/websocket/{client,protocol}` is migrated to the in-tree equivalents.
- `bridge service up` and the supervisor launchd script supervise one process, not two; `bridge service logs` is a single log file. The LaunchAgent plist and `install/bridge.sh.tmpl` are rewritten together — they are not optional.
- The default `bridge-cmd --server` URL stays `ws://localhost:3001`; existing scripts and agent integrations keep working. The semantic of that URL changes from "ws-server in the cloud" to "bridge-core control plane on this machine" and the README architecture table reflects that.
- The `ConnectionRegistry` abstraction is **retained as a `Map<browserId, BrowserConnection>` — multi-browser is genuinely supported at runtime, not just type-level**, because each extension instance owns a stable `browserId` and dials bridge-core's 3002 with its pairing token. What is single-browser today is the surrounding glue: the install path (one `bridge-core` process per user), the supervisor (one LaunchAgent), the status API and the `bridge` CLI (`bridge --browser <id>` takes an id but `bridge browser:list` is the only multi-id surface; nothing in `bridge service` is id-aware), and the popup (one browserId displayed). A future "two extensions on one machine" requirement would not need a code change in registry or its WebSocket plumbing — only in those surrounding components — so we do not need a follow-up ADR to widen registry itself. **Note what the tracked handle points to changes. Before the merge it tracked inbound `ServerWebSocket<WsData>` instances on ws-server — i.e. the upstream WS that local-proxy used to dial ws-server. After the merge the equivalent of that handle is the inbound `ServerWebSocket<undefined>` that the extension dials into bridge-core's `LocalServer`-equivalent port (3002). The class name and surface stay; the *role* the registry plays shifts from "which local-proxy is currently connected" to "which extension is currently connected" — the index keys on `browserId` either way, but what the value points at is a different WebSocket now.**
- Reconnect semantics are unchanged. The extension side already owns the retry loop — `apps/extension/src/offscreen.ts` schedules a fixed-3s reconnect on close/error, no backoff. `bridge-core` is the inbound WebSocket endpoint; on crash the LaunchAgent's `KeepAlive=true` brings a fresh process up on 3002, the extension's reconnect lands, and pairing (still a long-lived bearer token, hash stored on the bridge-core side) is unchanged across restarts. No new retry/backoff policy is needed in bridge-core; the extension's existing loop covers it.
- The bridge's auth shape is unchanged: extension↔bridge-core uses the existing pairing token; CLI/MCP↔bridge-core still relies on loopback plus an optional `ApiKeyAuthProvider` for non-local deployments. Pairing is **not** extended to CLI/MCP — they are user-invoked processes under the user's control, not the threat pairing exists to address. The pairing token itself is a long-lived bearer (no expiry); revocation is operational — deleting `extensionTokenHash` from `~/.browser-bridge/config.json` causes the next extension reconnect to 403 and forces the user through the popup-driven re-pairing flow.
- Existing v0.2.x users cannot upgrade in place: the install pipeline requires a reinstall (different binary set, different LaunchAgent payload). On reinstall `install.sh` detects a legacy config (`~/.browser-bridge/config.json` written by an old binary) and **force-reinitializes it** — clears the extension token hash so the next extension reconnect is forced through pairing again, and regenerates `browserId` so old tool local sessions pointing at the previous browserId do not silently hit a fresh process. The release notes call this out.
- `CONTEXT.md` gains two terms — `Control plane` (the bridge-core WebSocket role, 3001) and `Browser connection` (the bridge-core outbound WebSocket client to the extension) — replacing the README's now-obsolete "WebSocket Server" and "Local Proxy" rows. A third entry — `Pairing` — is also added to make the long-lived-token invariant (no expiry, hash-side revocation) explicit instead of leaving it as an implementation detail of `apps/local-proxy/src/pairing.ts`. The README and `README_CN.md` lose the "WebSocket Server" / "Local Proxy" rows and the "云端 / 共享" wording.
