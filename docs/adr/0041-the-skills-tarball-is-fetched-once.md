# The skills tarball is fetched once, not once per target

ADR-0015 made skills default-on and shipped `browser-bridge-skills-<version>.tar.gz` as a release asset. It closed with a trade: *"With two default targets the tarball is downloaded once per target; the asset is a few KB, so the duplication is accepted in exchange for keeping `download_skills` untouched."* The installer therefore looped over its targets with the **whole pipeline inside the loop** — download, sha256 fetch, sha256 verify, extract, shape check — and a user with both `~/.agents` and `~/.claude` (the pair ADR-0015 defines as the defaults) watched the same asset and the same checksum arrive and be unpacked twice on every install and every `bridge service update`.

That trade was made against a different set of facts. The asset is no longer one small skill: it now ships `browser-bridge` **and** `browser-bridge-memory` (ADR-0039), and the `.sha256` sidecar is fetched and compared per target as well. More decisively, the reason given — *keep `download_skills` untouched* — described a cost, not a constraint. There was never a dependency forcing the download to live inside the target loop. It was where the code had put it, and `download_skills` doing "fetch and install one target" was simply one function that had grown two jobs.

Duplication is also the wrong shape for this asset. The installer is already fetching from a release URL, and the same install then pulls the runtime tarball, the extension zip, and their checksums — every one of those exactly once. Re-fetching the skills asset N times made the install's own traffic pattern a function of how many agents the user happened to run, which is not a property the release contract mentions and which no test covered. The installer was the only place that knew how many targets there were, so it was also the only place that could avoid the repeat.

**The fetch is now separated from the install.** `fetch_skills` downloads, verifies and extracts into a workdir owned by `main()`, and stops there. `install_staged_skills` copies that one verified tree into each target. The number of network fetches is one, whatever the target count.

The workdir lifetime moved with it. `download_skills` owned its `mktemp -d` through a `trap ... EXIT`, which was there because `die()` exits the shell and a `RETURN` trap would never fire. That only held while the whole thing ran in the install's own process; once the fetch moved into the subshell that converts `die()` into a warning, `die()` exits *that* subshell and the trap cleans up a directory whose parent shell is still going to write into. So the workdir is created and removed by `main()`, which is the process that actually owns it, on both the success and failure paths — the BB-E211 no-leak guarantee the existing suite asserts is now a consequence of the structure rather than of a trap's shape.

## Consequences

- One `GET` for the tarball and one for its `.sha256`, per install, regardless of how many of `~/.agents/skills` and `~/.claude/skills` exist. A BATS case counts requests in the mock server's access log to hold that.
- Nothing else about the skills step moved. Per-target failure isolation is unchanged — one bad destination still degrades to a warning while the others install — and so are the `--skills-dir` override, `--no-skills`, the replace semantics (`rm -rf` before copy), and the best-effort degradation of a failed fetch. Only the warning text changed, because a fetch failure now happens once, before any target is touched, rather than once per target.
- The check the code buys is a test rather than a comment: the duplication was invisible to the suite because no assertion looked at how many times the asset was requested. A regression now fails a test.
- `download_skills` is gone as a name. Nothing referenced it but the loop it sat in, and the two halves it conflated have different failure modes: the fetch fails for the whole install, the install fails for one target.
- This amends ADR-0015's trade-off only. Its decisions — default-on, the two default targets, parent-directory detection, replace semantics, best-effort — all stand.
