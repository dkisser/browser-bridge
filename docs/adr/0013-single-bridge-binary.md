# Merge bridge-core into bridge as a hidden serve subcommand

ADR-0012 shipped the control plane and the CLI as two Go binaries: `bridge-core` (control plane + MCP + extension bridge, configured from the `BRIDGE_*` environment) and `bridge` (cobra CLI + the `service` lifecycle tree). That split mirrored the Bun-era artifact layout, not any real independence: the daemon has exactly one caller — the CLI's own service layer (`spawnCore`, the launchd supervisor) — and the two must move in lockstep because they share the wire envelope, the ports, and the release. The cost of the split is concrete: the tarball carries two static binaries (~13.4 MB + ~12.8 MB on darwin/arm64) whose Go runtimes and shared packages (`internal/core`, `internal/ws`) are duplicated, and a partial update can leave a mixed-version CLI/daemon pair behind.

Both binaries are merged into a single `bridge`: the daemon becomes the hidden subcommand `bridge serve` (cobra `Hidden: true`, so the public command set is unchanged), reading the same `BRIDGE_*` variables, initializing logging the same way, and calling `app.Run` exactly as `cmd/bridge-core` did. The env parsing moves into `internal/app` as `ConfigFromEnv`; `cmd/bridge-core` is deleted. The supervisor spawns the daemon by exec-ing itself — `exec.Command(e.BridgeBin(), "serve")` — and the single link-time `version` now feeds both `bridge --version` and the MCP server. One ~17.7 MB binary replaces the ~26.2 MB pair.

## Considered Options

- **Keep two binaries**: preserves the status quo layout but keeps the duplicated-runtime tarball cost and the mixed-version failure mode, while buying nothing — no second consumer of the daemon binary exists.
- **Merge, with `serve` as a visible command**: the CLI instruction set is a stable contract (users and scripts parse `--help`), so the subcommand is hidden; making it visible would silently grow the public surface.
- **Point launchd straight at `bridge serve`, dropping the supervisor**: rejected — it would throw away the ADR-0005 design (foreground supervisor with a crash budget, pidfile ownership, clean TERM-grace shutdown) that `service up/down/status` builds on.

## Consequences

- `internal/cli/serve.go` wires the subcommand: `app.ConfigFromEnv()` (moved verbatim from `cmd/bridge-core/main.go`), `cfg.Version` from the binary's link-time version, `log.Default()`, and the command context (`Execute` already cancels it on SIGINT/SIGTERM). Daemon behavior is byte-identical to the old binary.
- `spawnCore` execs `$BB_HOME/bin/bridge serve`; `Env.CoreBin` is gone. Process-identity matching (`classify`, the "is this pid really ours" check) switches from the globally unique binary name `bridge-core` to the full `<BridgeBin> serve` command line — strictly more precise, since a subcommand name alone cannot distinguish sibling installs.
- The LaunchAgent plist template is unchanged: it already bootstraps `bridge service up --foreground` (the supervisor); only the supervisor's child process changes. Already-rendered plists keep working.
- The *service* keeps the bridge-core name: `bridge-core.log`, `bridge-core.pid`, the bash-parity status/help text, and all BB-E### codes are unchanged. `service doctor` collapses its two binary-presence checks into one (`bridge` is now the only binary).
- `bridge --version`'s default becomes `0.3.2` (was `dev`) so the MCP server keeps reporting the version the standalone daemon hardcoded; release builds override both through the same `-X main.version=...`.
- Upgrade transition: a pre-merge daemon (the standalone `bridge-core` process) classifies as "foreign" to a merged CLI, but `bridge service down` still stops it (the stop path checks pidfile + liveness, not identity). `install.sh` removes `$BB_HOME/bin/bridge-core` and restarts the service — that install-side landing (install.sh, `.github/scripts/build-binaries.sh`, `package.json` scripts, README/AGENTS references to `cmd/bridge-core`) is a follow-up commit; this commit is the Go-side landing and leaves those references stale on purpose.
- This evolves ADR-0012 rather than reversing it: the Go rewrite of both halves stands; only the packaging (one binary instead of two) changes. Wire protocol, ports, lifecycle semantics, and the e2e suite (which drives `app.Run` directly) are untouched.
