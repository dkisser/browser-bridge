# Dismissal is a stance the agent can read

An Approvals card gets a close affordance in its top-right corner. Pressing it does not delete the record and does not approve or deny anything: it records that a human has seen this request and does not want to answer it now, and it makes that stance readable to the agent on its next attempt. This amends ADR-0038, which decided where the permission mode sits relative to the Working scope, by making the mode part of what a dismissal is keyed on.

The key is `(origin, command, mode)`. A dismissal made in `standard` says "at this threshold, stop asking me about this"; switching to `strict` asks again, because that is a tighter threshold and the human has not restated their answer there. This makes the mode part of a dismissal rather than a property of one, which is the same move ADR-0038 made for the gate itself: the mode moves what an approval means, so it belongs in the key rather than beside it.

A dismissed request still produces a card, so a retried origin holds exactly one card and the human keeps the visibility to change their mind while the agent is told to stop knocking. Suppressing the card would have made a dismissal a quieter deny, which is the one thing the affordance must not be. The one-card invariant is **not** a property of `denialKey`, which is `reason|origin|command` (`packages/shared/src/policy.ts:540`) and therefore treats a retried-and-ignored request as a *different* entry from the one that was there before. `recordDenial` grows a `sameRequest` predicate for exactly this (`apps/extension/src/policy-state.ts:284`), widening the match to ignore the reason when both sides are origin requests. Deleting it as redundant would stack two cards for one request, one calling the origin unapproved and the other calling it closed.

The agent reads the stance through text, because there is no push channel: `humanDenialMessage` is a terminal string built in the shared package (`packages/shared/src/policy.ts:482`), Go only passes it through (`apps/bridge-core/internal/cli/send.go:110`), and the offscreen document never emits unsolicited events. The text says the human has declined to answer for now, and explicitly hands the decision back — "if this blocks your task, tell the human" — because a dismissal that reads as a refusal converts "I am busy" into "never ask again". That word is also why the current ending, "then the command can be retried", is wrong here and must be replaced.

The card a retry produces is not a dead end and not a trap. It carries the same Session / Always / Deny answers as the card before it, because a dismissal has to stay one click from becoming a decision — a close with no way back would be the failure mode this ADR exists to prevent. It also keeps the close, where pressing it takes the card away and leaves the stance as it stands: the stance is already recorded, and removing the control would leave the human holding a card they cannot remove, holding the badge at one for as long as the agent keeps asking.

A dismissal is cleared when the origin is granted (`approve-session` / `approve-always` drop it, since ignored and approved at once is a contradiction the human cannot have meant) and when the browser session ends (`clearSessionScoped`, alongside session-scoped approvals). `allow-once` does *not* clear it: that grant is scoped to a capability for one attempt, so it is not an answer about the origin and cannot answer a dismissal of some other command there.

**Known gap, deferred rather than solved.** A stance has no surface of its own — `OriginsPanel` lists `origins` and `deniedOrigins` only — so the human cannot see what they have ignored, and the only ways out are a grant or a denial. Both are *coarser* than the thing being escaped: a stance is (origin, command, mode), while a grant or a denial is the origin in every command and every mode. So the escape hatch is strictly wider than the decision it reverses, which means "v1 has no un-ignore control" is true only in the sense that it has no *narrow* one. A read-only row per ignored stance in the Origins panel, and clearing from there, is the thing that would actually close this — recorded here because the reasoning for deferring it is a reason and not a decision, and the next reader should be able to tell the difference.

## Considered Options

- **Pure UI dismissal** (remove the card, touch no state): rejected, and not for cost. `dismiss` only filters the entry out of `recentDenials` (`apps/extension/src/policy-operations.ts:118`), and `recordDenial` re-creates it on the next identical rejection, so the card returns in place and the agent's text is byte-identical. Against an origin that keeps getting rejected it buys nothing — the noise leaves the screen and stays in the agent's loop.
- **Whole-origin dismissal** rather than per command: rejected. A human who is tired of `tab:new` opening new tabs has not decided anything about `click` on that origin, and a narrower human decision should not widen itself. The same argument later ruled out letting `allow-once` clear a stance: a one-shot screenshot grant is an answer about a capability, not about the origin.
- **Keep an audit trail of dismissals now**: deferred to ADR-0017's audit work. The stance is already in policy state under this design, so the trail has something to read; writing a second record now reserves a schema for storage that does not exist yet.

- **A red `×` matching the side-panel message dismiss**: rejected on color. Red is the Deny semantic in this UI, and a dismissal is not a denial; the icon is neutral (`--text-faint`), composing TakeoverHero's ghost icon button (22×22, chip surface on hover, visible focus ring) rather than copying it, permanently visible rather than hover-revealed, because a control that only exists under the cursor is not a control you can aim at.

## Consequences

- The close appears on origin-request cards — `origin_not_approved` and `origin_ignored`, both via `isOriginRequestReason` (`packages/shared/src/policy.ts:56`), and only where the denial carries an origin, since `applyDenialAction` records no stance without one. Every other reason already carries a Dismiss text button (`apps/extension/src/ui/policy-actions.ts:13`), and the same action in two forms in one panel is a way to have two ideas about one button.
- The set of origin-request reasons lives in **one** predicate rather than at each of its four call sites (the reducer, the close affordance, the button set, the denial dedupe). They spelled it out separately once, and the first implementation passed an eleven-test suite while three of them disagreed.
- `denialCardButtons` is documented as copy-frozen ("order and labels are user-visible contract"); the new affordance is outside that function and does not disturb the frozen triads.
- A new `DenyReason` (the ignored stance) is distinct from `origin_denied`, which stays a hard rail in every mode (`packages/shared/src/policy.ts:363`). Ignoring is not refusing: the origin can still be granted later, and the dismissal itself expires with the session.
- `Denial` carries the mode the decision was made under, and the Go struct mirrors it (`apps/bridge-core/internal/core/wire.go`). It has no consumer yet, which is exactly why `TestPolicyDenialSurvivesTheWire` asserts it — a field nothing reads drifts silently.
- The badge counts `recentDenials.length + pendingDownloads.length` (`apps/extension/src/policy-state.ts:331`), so a dismissed-then-retried request still shows in the count. That is intended — the human is being asked again.
